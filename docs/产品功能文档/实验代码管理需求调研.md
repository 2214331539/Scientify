# Scientify 实验代码管理需求调研

调研日期：2026-10-01。用途：为 [实验代码管理详细产品设计](实验代码管理详细产品设计.md) 提供依据。本文完成的是桌面研究、公开用户问题分析和本项目源码核查；未开展真实用户访谈、问卷或可用性测试，不把竞品功能等同于已经验证的 Scientify 用户需求。

## 调研结论

建议优先服务在本机推进计算实验和数据分析的研究者，帮助他们回答五个日常问题：现在用的是什么环境，实际运行了哪份代码，任务是否还在运行，这次结果在哪里，以及下次如何按相同条件再试一次。全局 AI 可以承担准备和开发，但运行记录应由应用根据真实进程与文件建立。

首批验证假设是 **Python 优先、AI 与手动编辑并重**。这不是用户已经确认的语言和使用习惯；对 R、Julia、C++ 等保留自定义命令入口，不在第一阶段承诺同等深度的环境管理。Notebook 是潜在的重要需求，暂不因“科研用户会用”这一推测而把完整 Jupyter 内核系统塞入首版。

首版的主要价值应是少填表、少找日志、少丢运行上下文。复杂调参、模型注册、云端 GPU、论文自动生成都不能代替这个基本体验。

## 本产品用户已经说明的需求

| 用户要求或已反馈问题 | 实验页面应落实的要求 |
| --- | --- |
| 根据自然语言在本地创建代码环境并开展实验 | 不只提供聊天建议；有目录、环境、命令、进程和结果的实际落点 |
| AI 是全局的，不按导航页割裂入口 | 实验页操作复用全局助手；页面改变不自动改绑历史会话 |
| 文献与代码工作区需要记忆、操作边界 | 会话显示绑定项目与根目录；实验工具按代码域校验范围 |
| 多项目、多会话必须能同时运行 | 后台任务属于运行时；导航、切会话和编辑不被全局 loading 锁住 |
| 中止失效、流式输出卡顿曾影响验收 | 停止以真实进程退出为准；日志分批显示，前端不卡顿；不能用停止动画冒充停止任务 |
| 每次启动不应弹出终端窗口 | 命令和日志在应用内呈现，后台启动不弹出独立控制台 |
| 允许手动配置模型服务商 | 继续复用 AI 侧栏的模型配置，不在实验页复制配置表单 |
| 不做文献语料库、不做证据到论文闭环、暂不做云端执行 | 本阶段围绕本地代码、环境、实验运行和结果；不把被排除的方向设为前置依赖 |

这些是本产品最直接的需求证据，优先级高于旧路线图和竞品功能表。

## 用户工作流与失败点

以下用户类型是用于设计的情境分类，不是已招募的访谈对象。日常研究同时可能涉及多种情境，不按学科强制分产品。

| 情境 | 用户希望完成的事 | 需要观察的失败点 | 产品假设与优先级 |
| --- | --- | --- | --- |
| 接手导师或论文作者的项目 | 指向现有目录并成功运行最小示例 | 不知道用哪个 Python、依赖装到了另一个环境、README 命令不适合 Windows | 自动发现环境、展示完整命令与工作目录，提供最小试跑；首版 |
| 从零写数据分析或仿真 | 描述输入数据与目标，让 AI 建文件后能手动接管 | 生成了代码但没有环境、数据路径或结果位置 | 一条自然语言任务关联实际文件与运行配置；首版 |
| 修改参数验证一个想法 | 保留旧结果，跑新的参数，比较变化 | 覆盖同一输出目录、参数记在聊天里、同一 commit 隐藏不同本地修改 | 每次运行独立 ID、参数快照、代码状态、输出位置；首版 |
| 让实验跑十几分钟到数小时 | 去读文献或做另一个项目，回来检查 | 标签关闭后不知道任务还在不在、中止只停掉界面、CPU/GPU 被抢占 | 后台任务入口、真实状态、进程树中止、可解释队列；首版 |
| 实验失败 | 找到第一处可行动的错误，修复后重跑 | 只看到非零退出码、日志被截断、误把 stderr 警告当失败 | 可搜索日志、错误定位、带上下文交给 AI、保留原失败运行；首版 |
| 一周后回到实验 | 找到当时的代码、参数、环境和产物 | 只剩一张图、环境已改变、未提交修改已丢失 | 自动记录来源与条件，清楚区分“记录完整”和“可恢复执行”；首版至下一阶段 |
| 少量方案对比 | 判断差异是否来自参数，而不是数据或评估方法 | 同名指标不同单位、缺失值被当成 0、单次最优被误当显著改善 | 对齐参数、数据集、评价条件，缺失值明确显示；首版基础表格 |
| 已用 Notebook、VS Code 或 MLflow | 在 Scientify 组织工作，又能继续用现有工具 | 被迫迁项目、改所有训练代码、装一个新的平台服务 | 原目录接入、外部工具入口、逐步导入结果；首版兼容，深度集成后置 |

## 外部资料如何影响设计

| 核实的来源事实 | 对 Scientify 的推断 | 对应详细设计 |
| --- | --- | --- |
| 科研实践建议把项目置于独立目录，区分原始数据、结果和代码，并记录数据处理步骤 [R1] | 接入现有目录、不强制重排；为新建项目给轻量模板，输入与产物分别登记 | 目录接入、输入与产物 |
| VS Code 的 Python 环境文档将解释器发现、选择、环境管理放在工作区体验中 [R2] | 环境必须显式可见，不能只依赖用户终端当前激活了什么 | 环境入口与运行前检查 |
| uv 项目使用 `.venv` 和 `uv.lock`，通过 `uv run` 执行项目命令 [R3] | 可复用现有环境工具和锁文件；不必自建包管理器，也不能把锁文件等同于完整机器镜像 | 环境与依赖 |
| VS Code Tasks 区分命令、参数、工作目录和环境，允许组合任务和并发限制 [R4] | 运行配置应是可复用对象，不应从聊天文本中反复猜命令 | 运行配置、并行调度 |
| JupyterLab 关闭文档后内核或终端仍可运行，Running 面板负责找回和关闭 [R5] | 切页只改变查看对象；统一后台入口比每页单独 spinner 更适合长任务 | 后台运行、停止与退出 |
| MLflow 将一次代码执行定义为 run，记录参数、指标、时间和产物 [R6] | 一个会话可以产生多次运行；一次运行必须有稳定身份，与 AI 回复是否结束分开 | 对象模型、运行详情 |
| DVC 的实验支持参数、指标和图的追踪；队列运行在临时目录隔离，默认串行且可设多 worker [R7–R8] | 输出隔离、代码副本、资源并发是三件不同的事；不能将“开多个进程”叫作完整隔离 | 并行边界、后续代码副本 |
| W&B Run Comparer 并列显示配置和指标，帮助观察变更与结果的对应 [R9] | 默认先用差异表回答“改了什么”；复杂图表不是第一步 | 运行比较 |
| Aim 用 SDK 记录参数和指标，用本地 UI 查看结果 [R10] | 数据采集与呈现可分离；先兼容简单结构化结果，不强迫用户替换原脚本 | 指标接入与工具兼容 |
| MLflow 用户报告：未提交修改前后两个实验显示同一 commit，容易误以为代码相同 [R11] | 同时记录 Git 状态、未提交变化和实际源文件快照；不只保存 commit | 代码版本与再次运行 |
| Jupyter 用户报告执行教程时找不到 bash，又遇到 TensorFlow 模块缺失 [R12] | Shell、解释器、依赖应分别检查；提示要说明“用哪个程序在哪个目录执行” | Windows 行为、环境诊断 |

R11 是 2019 年创建、2023 年关闭的历史问题；R12 是 2020 年创建并关闭的历史问题。引用目的是研究失败模式，不据此评价这两个项目当前版本的质量。

## 开源组件和竞品的取舍

| 方案 | 值得借鉴或复用的部分 | 本次建议 |
| --- | --- | --- |
| 已内置的 Codex harness | 会话、模型调用、代码编辑、命令与工具交互 | 继续作为执行代理；实验运行的稳定记录和进程管理由 Scientify 集成层负责 |
| Python venv 与 uv | 环境创建、依赖解析和锁定、项目命令 | 复用已有安装；新下载需用户发起。后续打包 uv 须另核版本、分发许可和更新机制 |
| MLflow | 运行、参数、指标、产物的对象模型与导入接口 | 先兼容现有结果；不在首版强制捆绑 Python 服务或完整 MLflow UI |
| DVC | 数据与参数版本、临时实验目录、实验队列机制 | 借鉴隔离方式；不强制每个项目先建立 DVC pipeline |
| Aim | 本地指标记录与可视化 | 作为后续适配候选；不让所有用户先改写成 Aim SDK |
| VS Code 与 JupyterLab | 环境可见、运行与视图解耦、外部开发兼容 | 保留外部打开。完整调试器、扩展系统、Notebook 内核另立设计 |
| W&B | 参数与结果并列比较的交互 | 借鉴比较方式；本次不引入云服务依赖 |

这是产品层面的组件取舍，不是许可证审计或打包兼容性测试；没有宣称上述工具已经接入。首版运行索引可以采用现有 Rust 与本地存储体系，不需要为了“实验追踪”先引入一整套平台。

## 尚待验证的需求

最值得优先验证的是：用户是否愿意把正式运行交给 Scientify 管理，以及是否愿意用脚本或命令完成第一阶段实验。如果大多数目标用户必须使用逐单元 Notebook 才能完成工作，单纯延后 Notebook 会影响产品适用范围，需要在编码前调整。

| 假设 | 建议验证方式 | 影响决策的信号 |
| --- | --- | --- |
| Python 足够覆盖首批任务 | 请目标用户展示最近三个真实实验的语言、入口和环境 | 若多名首批用户依赖 R/Julia 或复杂编译链，调整首期支持范围 |
| AI 与手动编辑并重符合习惯 | 观察一次从需求到运行的过程，不提示使用方式 | 用户何时检查或接管代码，是否需要在外部编辑器工作 |
| 独立运行记录能降低维护负担 | 比较同一任务当前做法和原型做法，记录手工填字段与寻找文件次数 | 若仍需大量复制聊天和命令，应优先改自动采集，不加更多图表 |
| 当前目录执行可作为首版默认 | 让用户一边运行一边修改代码，观察是否理解共享文件提示 | 若频繁动态读代码或并行改同一文件，应提前交付独立代码副本 |
| 少量对比表优先于实时曲线 | 让用户解释最近一次选择实验方案的依据 | 若核心决策依赖训练曲线而非末值，提升曲线优先级 |
| 关闭应用后停止可接受 | 询问真实的长任务时长、睡眠和关机习惯 | 若日常要求跨应用退出持续训练，本机常驻进程应另做设计；不能默认为云端需求 |

建议后续招募 6–8 名正在做本地计算研究的用户，覆盖脚本分析、机器学习、数值仿真与 Notebook 用户，进行一次 45 分钟观察和约一周试用。此样本只用于发现工作流问题，不用于推断市场比例。

访谈按真实任务推进：展示上次运行 → 找到当时命令和环境 → 修改一个参数 → 找到旧结果 → 说明如何停止 → 找回一周前的版本。避免只问“你想要哪些功能”。素材留在用户设备，允许脱敏；本次没有向任何人发送访谈邀请。

原型验证建议任务是：接入一个已有目录，完成一次运行，切换到另一个项目继续工作，中止其中一个任务，比较两次结果，再找到它们使用的参数和代码。记录操作是否成功、需要多少提示、错误如何恢复，不以好看或“愿意尝试”替代证据。
