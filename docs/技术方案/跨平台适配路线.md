# Scientify 跨平台适配路线

状态：2026-10-03 源码核对与实施建议，尚未执行 macOS / Linux 适配。已交付及验证的桌面版本为 Windows x64；浏览器预览不是完整 Web 版。

## 推荐方案

继续使用现有 Tauri 2、React 和 Rust，共用 UI 与领域逻辑，通过小范围平台适配逐步支持 macOS 和 Linux。无需为跨桌面平台更换 Electron、Flutter 或重新开发前端。

第一阶段建立能编译、启动并可靠保存本地资料的桌面版本，再接入实验执行、Agent 和内嵌浏览器。缺失能力应明确禁用；浏览器适配期间可以提供系统浏览器入口，但不得把它描述为已支持内嵌浏览。

| 进程与终端 | 使用 portable-pty；Windows 有 ConPTY、Job Object 和专用静默启动路径，部分非 Windows 分支已存在                                                       | 复用 PTY 接口，核对 POSIX shell、进程组、子进程树停止和退出清理；不要假设 Windows 沙箱行为可直接移植         |

| 打包       | [Tauri 配置](../../src-tauri/tauri.conf.json)只配置 NSIS                                                                                             | 增加分平台配置及 `.app` / DMG、AppImage / deb 等目标，保留统一应用标识与数据迁移约定                         |

## 实施顺序与验收

1. **构建与启动**：增加 OS / architecture 解析与分平台配置，在 GitHub Actions 的 Windows、macOS、Linux runner 分别构建。先选择一个 macOS 架构和一个 Linux 发行环境验证，其他目标另列状态。
2. **文件与工作区**：验证项目创建、目录关联、PDF 阅读、Markdown 自动保存、外部冲突、退出再开和数据备份。以真实临时目录验证，不使用用户材料。
3. **手动实验**：验证 Python 发现、venv、真实终端、stdin、独立停止、日志和产物；进程结束后不能残留子进程。
4. **AI 与浏览器**：验证各平台引擎的实际权限与审批，以及原生网页的导航、下载和 IPC 隔离。未通过的能力继续显示准确限制。
5. **分发**：macOS 签名、公证与 Gatekeeper；Linux 选择明确支持的发行版及依赖基线；逐平台测试安装、升级和数据保留，再发布对应安装包。

本方案不提供未经实测的工期承诺。应用的大部分界面可以复用，但原生浏览器、沙箱与分发是实际成本；编译成功不等于功能已经跨平台。

## Web 与移动端

现有 React 界面可用于低成本的浏览器演示，但普通网页不能直接承担任意本地目录访问、Python 进程、Git、PTY 与桌面 Agent。要提供完整 Web 服务，需要另建受认证和权限约束的后端或本地伴随服务，并处理账户、存储及任务执行，不属于简单部署静态前端。

移动端建议先验证阅读、笔记和只读结果的需求。桌面进程、Python 环境和工作区文件权限不能直接搬到手机；同步和服务端能力也尚未实现。当前优先交付 macOS / Linux 桌面适配。
