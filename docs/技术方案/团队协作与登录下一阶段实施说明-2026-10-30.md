# 团队协作与登录下一阶段实施说明

## 本阶段目标

本阶段把启动项目页中的“团队协作空间”从占位页改成可用的协作入口，并让登录、远程项目和成员管理沿用现有本地优先架构。桌面端通过 Tauri IPC 调用协作服务，React 页面不直接持有 JWT，也不直接访问文件系统。

## 已接入的用户流程

1. 用户进入启动页的“团队协作空间”。
2. 桌面端默认连接 Scientify 托管协作服务；自托管部署可在“高级”设置中替换地址。
3. 输入手机号并获取短信验证码。未注册手机号在验证通过后自动创建账号，登录状态通过短期访问令牌与轮换刷新令牌维持在单台设备。
4. 登录成功后加载用户可访问的远程项目。
5. 可以创建协作项目、查看项目成员、邀请成员并选择成员角色。邀请尚未注册的手机号时保留待加入记录，对方首次登录后自动加入项目。
6. 点击“进入项目”时，先绑定远程项目，再将远程项目镜像为本地项目记录，最后打开现有 Scientify 工作区。
7. 文献页继续使用已有的首次上传、outbox、冲突队列和 inbox 应用流程；AI 的官方模型调用继续复用服务端网关。

## 模块边界

```text
CollaborationWorkspace
  └─ platform/collaboration.ts
      └─ Tauri IPC
          └─ src-tauri/src/collaboration.rs
              └─ server / PostgreSQL / OSS
```

- `CollaborationWorkspace` 只负责登录和协作项目交互，不读取本地文件，也不保存令牌。
- `platform/collaboration.ts` 只定义前端可用的类型和 IPC 调用。
- Rust 负责 endpoint 校验、令牌刷新、令牌文件读写和受信 WebView 校验。
- 服务端负责手机号验证码、JWT、成员 ACL、同步元数据和 OSS 签名地址。
- `App.tsx` 只负责把远程项目映射到现有本地 `Project` 模型，不改变文献、代码和 AI 工作区的职责。

## macOS 适配

协作页面复用 React/Tauri 同一套布局，认证和 HTTP 逻辑不依赖 Windows 路径或进程 API。macOS 配置的最低版本已与 CI 的 macOS 14+ 验证目标一致，Unix 进程模块继续由 `src-tauri/src/lib.rs` 显式注册。macOS 发布仍由 `.github/workflows/macos.yml` 构建 `.app` 和 `.dmg`。

托管协作服务地址是应用内的产品配置，不是秘密；需要改绑自有域名时可在构建时设置 `SCIENTIFY_COLLAB_ENDPOINT`，未设置则使用产品默认地址。协作服务器的 `DATABASE_URL`、`JWT_SECRET`、OSS AccessKey 和短信 AccessKey 只存在于服务端部署环境，不要求 Mac 构建机或 Windows 构建机提供。Mac 本机构建仍需要 macOS 14+、原生 arm64 Node 24、pnpm 10.11.0、Rust stable、Xcode Command Line Tools 和 Python 3。

## 当前边界

协作身份、项目入口和远程文献同步已经接入。代码编辑现在也会沿用本地优先原则：本地保存成功后把 `code-upsert` 快照写入 outbox，服务端按实体 revision 接收，远端变更进入 inbox，由用户在协作设置中显式应用；工作区打开时会静默同步，但文献页只应用文献域，代码域不会绕过用户确认自动写入。应用代码变更时会按 worktree 根目录、相对路径和本地文件版本做安全检查，版本不一致则保留本地文件并进入延期队列。只读成员可以拉取变更但不能提交。删除、重命名和二进制资源同步仍未接入，跨设备 worktree 的稳定映射也需要后续把实验登记同步到服务端，不能把本地绝对路径当作远程权限标识。

## 下一阶段计划

1. **补齐代码文件操作**：为删除、重命名和复制增加 `code` 域操作，并沿用 `ResearchFiles` 的路径和版本校验。
2. **成员权限落地**：将 owner/editor/reviewer/viewer 映射到文献上传、代码写入、实验运行和邀请成员四类动作，前端在不可用动作上给出原因。
3. **冲突与历史**：为代码变更提供 diff、按单条变更应用/保留本地和历史查看入口，并把同步状态放入代码工作区顶栏。
4. **实验登记同步**：为实验 ID、worktree 标识和本地路径建立跨设备映射，避免远端变更依赖另一台设备的绝对路径。
5. **真实服务验收**：使用部署后的 PostgreSQL、OSS 和短信配置完成 Windows 与 macOS 登录、首次同步、断网重试、令牌刷新和跨设备同步验收。当前代码与客户端入口已准备，但生产机尚未建立 Scientify 专用数据库、服务进程和 Nginx `/v1/` 反向代理，因此不能把现有构建称为已验证的在线协作版。
