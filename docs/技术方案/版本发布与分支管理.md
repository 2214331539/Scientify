# 版本发布与分支管理

Scientify 只有一个长期分支 `main`。维护者和自动化助手直接在 `main` 上开发，日常更新与验收见[开发与验收流程](../开发流程/开发与验收流程.md)；外部贡献走 PR，命名见[贡献指南](../../CONTRIBUTING.md#分支与合并)。不预建 `develop` 或各类空分支。当前发布 Windows x64 NSIS 与 macOS 14+ Apple Silicon DMG 预览包，不发布 Intel / Universal。

## 两个仓库

| 仓库 | 可见性 | 用途 | 推什么 |
| --- | --- | --- | --- |
| [Tsingyu-x-THU/Scientify-Desktop](https://github.com/Tsingyu-x-THU/Scientify-Desktop) | 私有 | 团队日常开发 | `main` |
| [2214331539/Scientify](https://github.com/2214331539/Scientify) | 公开 | 发布 Release、接收 Issues 和外部 PR | `main` 和版本标签 |

- 同一个 `main` 推到两个仓库，提交完全相同；两边都只做快进推送，不强推、不改写历史。
- **Release 只在 2214331539/Scientify 发布**。`Desktop release` 工作流只在这个仓库运行；版本标签在 Scientify-Desktop 上即使存在也不会触发发布。
- 公开仓库的全部历史都对外可见，提交前确认没有密钥、密码、真实手机号和服务器登录信息。
- Windows 上的远程名：`tsingyu` 是 Scientify-Desktop，`origin` 是 2214331539/Scientify。

## GitHub 设置

- 默认分支：`main`。
- 外部 PR 的合并方式：squash merge；合并后自动删除任务分支。
- 主分支保护：禁止强推、禁止删除。维护者直接推送；外部 PR 要求 `windows` 与 `Apple Silicon build and native verification` 状态检查通过并解决全部讨论。
- 私有仓库的强制分支保护需要 GitHub 支持的付费套餐。若设置页提示未启用或不会强制执行，应明确记录此限制并按约定人工审阅，不能声称已受保护。公开仓库可按 GitHub 免费套餐的可用规则配置。
- 版本标签只由维护者创建，不改写已发布标签和资产。

## 创建版本

1. 在最新的 `main` 上同步更新 `package.json`、`src-tauri/tauri.conf.json`、两个 Cargo 包的版本；运行 `cargo metadata --locked` 前先更新 `Cargo.lock` 中的工作区版本，一起提交为 `chore: release <version>`。
2. 版本采用 `MAJOR.MINOR.PATCH`。试用版如 `0.3.0-alpha.1`，标签为 `v0.3.0-alpha.1`，也支持 `beta`、`rc`。在本次的[更新记录](../更新记录/README.md)里说明数据兼容性和验证结果。
3. 版本提交推到两个仓库，等 2214331539/Scientify 上 `main` 的 Windows 检查通过后，在 `main` 上创建带注释标签，推到 2214331539/Scientify（Windows 上的远程名是 `origin`）：

   ```powershell
   git switch main
   git pull --ff-only tsingyu main
   git push tsingyu main
   git push origin main
   git tag -a v0.3.0-alpha.4 -m "Scientify 0.3.0-alpha.4"
   git push origin v0.3.0-alpha.4
   git push tsingyu v0.3.0-alpha.4
   ```

   标签也推到 Scientify-Desktop，保持两边一致；那边不会发布。

   后续发布必须换成新的版本号，不能重复使用已发布标签。

   标签必须与四处版本号完全一致；日期、构建号等内容不能拼在版本标签后。例如 `v0.3.0-alpha.1-20261017` 会被视为错误标签，正确写法只有 `v0.3.0-alpha.1`。`Desktop release` 会先做轻量格式检查；格式不正确的标签不会启动耗时构建，也不会向维护者发送失败通知。

4. `Desktop release` 验证标签、四处版本一致、提交属于 `main`，然后安装锁定依赖、准备许可资源、运行 TypeScript / 前端 / Rust 检查、Windows 构建 NSIS 并执行隔离安装器验证。
5. 全部通过后，独立发布任务获得 `contents: write`，验证 SHA-256，上传 Windows 安装包到草稿，再转为正式可下载的 Release。Alpha/Beta/RC 自动标为 Pre-release，不设置为 Latest。无需个人访问令牌，使用该工作流的短期 `GITHUB_TOKEN`。发布说明顶部注明 macOS 安装包稍后补充。
6. **macOS 安装包在维护者的 Apple Silicon Mac 上构建**，再补充到同一个 Release：
   - 检出版本标签，运行前端和 Rust 检查，设置 `MACOSX_DEPLOYMENT_TARGET=14.0`、`SCIENTIFY_CODEX_TRIPLE=aarch64-apple-darwin`、`APPLE_SIGNING_IDENTITY=-`（ad-hoc 签名）和 `MACOS_SIGNING=adhoc`，执行 `node node_modules/@tauri-apps/cli/tauri.js build --bundles app,dmg -- --locked`；
   - 检查 DMG 完整性（`hdiutil verify`），把 app 只读挂载后复制到临时目录，确认 app 和 Agent 都是 arm64、签名有效、Agent 能输出版本号。**不要在自己的 Mac 上运行 `scripts/verify-macos.py`**：它会对 `~/Library/Application Support` 里的真实数据执行迁移并启动应用，只允许在 GitHub 的临时 runner 上运行（脚本本身也会拒绝）；
   - 运行 `node scripts/stage-release.mjs`，在 `.release/` 得到 DMG、`SHA256SUMS_macos_arm64.txt`、`RELEASE_NOTES_macos_arm64.md` 和许可清单；
   - 用 `gh release upload` 上传 DMG 和 macOS 许可清单，把 macOS 的哈希追加进 `SHA256SUMS.txt` 后重新上传，并把发布说明里“稍后补充”那一行换成 macOS 说明；
   - `macOS checks` 工作流仍会在每次推送 `main` 时运行，在 GitHub 的 Mac runner 上做完整的原生验证，但不再参与发布。

## 分发内容与验证边界

- `Scientify_<version>_windows_x64_setup.exe`：当前用户安装，包含应用、固定版本 Agent 及依赖许可。WebView2 缺失时在线安装运行时。
- `Scientify_<version>_macos_arm64.dmg`：Apple Silicon 原生 app 与 arm64 Agent。
- `SHA256SUMS.txt`：两个安装包的 SHA-256。
- `THIRD_PARTY_LICENSES_windows_x64.txt` 与 `THIRD_PARTY_LICENSES_macos_arm64.txt`：各目标依赖许可报告；安装目录 `licenses/` 还包含完整 Agent 与 PDF 资源声明。
- GitHub 自动附加该标签的源代码压缩包。

安装器验证仅在 GitHub 临时 Windows runner 上运行，检查隔离安装、Agent 可执行、重复安装和卸载后保留 `ScientifyData`。不会在开发者电脑上静默安装/卸载应用，也不代替交互式桌面、升级迁移或模型效果验收。发布页如实列出验证范围。

Windows 当前未签名，Mac 默认 ad-hoc 签名且未公证；当前无自动更新，不要求用户关闭系统防护。哈希校验只验证完整性，不等于发布者签名。更新前关闭应用，备份应用数据与外部目录；Python 和 Git 由用户按需安装。

## macOS 可选签名

`setup-macos-signing.sh` 支持仓库 Secrets：`APPLE_CERTIFICATE`（base64 p12）、`APPLE_CERTIFICATE_PASSWORD`、`APPLE_SIGNING_IDENTITY`、`APPLE_API_ISSUER`、`APPLE_API_KEY` 和 `APPLE_API_PRIVATE_KEY`（p8 内容）。完整配置后，CI 构建使用临时钥匙串进行 Developer ID 签名与公证，完成后删除临时签名材料；普通 PR 不读取凭据。当前仓库未配置这些凭据，macOS 安装包也改为在维护者的 Mac 上构建，发布页必须标注 ad-hoc / 未公证，不声称签名分发已完成。以后要做签名和公证，可以在本机钥匙串里配置 Developer ID，或者改回由 CI 构建 macOS 安装包。

## 失败与重试

测试、打包或安装器验证失败时不会创建可见 Release。排除临时网络故障后可重跑失败任务，或在 Actions 的 `Desktop release` 输入既有标签手动触发。需要改代码时在 `main` 上修复，再创建新版本标签，不移动旧标签。

已发布版本不可被重跑覆盖；未发布的草稿允许重试上传。若发布中断，先检查草稿和 Actions 日志，不直接把缺少验证或资产的草稿公开。首次下载也应确认 Release 的 Assets 包含安装包，而非只有源码。

仓库可见性与 Release 下载权限一致。私有仓库发布并不自动变为公开下载；面向公众分发时由仓库所有者单独决定开放源码与历史的可见性。
