# Scientify 协作服务与同步技术方案

状态：客户端同步基础第一阶段已完成。服务器地址暂由用户后续提供，客户端不得硬编码生产地址；当前仍不启动真实网络同步。

## 1. 架构边界

Scientify 客户端保留本地文献、笔记、代码、Git、Agent、Python 和实验运行。协作服务器负责用户、工作区、项目成员、变更版本、活动通知和共享对象。客户端通过 HTTPS REST 提交/拉取变更，通过 WebSocket 接收项目活动通知。

```text
React 设置 / 文献 / 代码页面
          │ typed platform API
Rust CollaborationService
          │ HTTPS + WebSocket
协作 API + PostgreSQL + 对象存储 + Git 服务
```

当前已保存服务器地址、本地同步状态和离线 outbox，不启动网络请求。每条 outbox 变更包含 `operationId`、`clientId`、`projectId`、`domain`、`entityId`、`baseRevision`、`kind`、`payload` 和创建时间；重复入队按 `operationId` 幂等处理，成功后删除，冲突则保留并标记。拿到服务器地址和 API 契约后，再实现身份和网络 transport。

## 2. 本地状态

协作配置保存为数据目录下的 `collaboration.json`，不进入模型配置，也不保存 API Key。状态包括：

- `enabled`：是否启用项目协作。
- `endpoint`：规范化后的 HTTP/HTTPS 基础地址。
- `workspaceId`：远程工作区 ID。
- `lastSyncAt`：最近成功同步时间。
- `pendingChanges`：本地待同步变更数。
- `conflicts`：待用户处理的冲突数。

后续增加 outbox 时，每条变更必须有 `operationId`、`clientId`、`projectId`、`domain`、`entityId`、`baseRevision` 和 `createdAt`，服务器按 `operationId` 幂等处理。

## 3. 文献同步

元数据和笔记通过项目 revision 同步；PDF 通过 SHA-256 内容寻址和可恢复上传。PDF 不依赖用户本地绝对路径，服务器只保存资源 ID、哈希、大小和项目内相对标识。删除通过 tombstone 传播，避免旧客户端重新创建已删除资源。

Markdown 笔记首版采用带父版本的三方合并，不能合并时返回冲突内容。CRDT 实时编辑不属于首期范围。

## 4. 代码同步

不实现自定义 Git 文件同步。协作服务器返回或管理标准 Git HTTPS/SSH 远程仓库，建议部署 Gitea 或 Forgejo。Scientify 继续复用现有 `git.rs` 和 worktree 能力，完成 fetch、pull、push、分支状态和冲突展示。运行记录绑定 commit SHA；代码之外的环境、密钥和数据不随 Git 自动复制。

## 5. 服务端建议

开发阶段可以使用 Rust Axum、SQLite、本地对象目录和 Forgejo；正式部署切换 PostgreSQL 与 S3 兼容对象存储。服务器不运行 Scientify Agent，不执行用户实验，不接收模型 API Key。

建议接口：

```text
GET  /v1/health
GET  /v1/workspaces
GET  /v1/projects
GET  /v1/projects/{id}/sync
POST /v1/projects/{id}/sync
POST /v1/blobs/init
PUT  /v1/blobs/{uploadId}
POST /v1/blobs/{uploadId}/complete
GET  /v1/projects/{id}/activity
```

## 6. 实施顺序

1. 客户端配置、协议 DTO、outbox 和冲突状态。（已完成）
2. 认证、工作区、项目成员与权限。
3. 文献元数据、PDF、笔记同步。
4. Git 远程仓库、分支、推送/拉取和冲突。
5. 运行记录、日志和选择性产物同步。
6. 实时笔记、评论和在线成员状态。

## 7. 安全边界

所有网络请求使用 TLS；服务器端按项目和成员权限校验；上传前明确展示文件范围；客户端不上传本地绝对路径、凭据、`.env`、虚拟环境或隐藏 Agent 数据。同步失败只能产生可见错误和可重试状态，不能返回假成功。
