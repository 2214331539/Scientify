# 商业化与管理后台设计方案

- **状态**：2026-11-16 评审通过，第一期已实现，见第十五节和[更新记录](../../更新记录/2026-11-16-商业化第一期.md)。定价按第三节执行；AI 对话的内容只存在用户电脑上
- **原型**：[管理后台原型.html](../演示/管理后台原型.html)。单个文件，直接在浏览器打开。左侧是后台的各个页面，右上角“用户端”能看到桌面应用里对应的变化。数据都是虚构的。
- **范围**：套餐、额度和计费规则；桌面应用里用户能看到的变化；服务器上的管理后台（概览、用户、团队、套餐与额度、模型与渠道、用量、订单、审计）；服务端的数据表、接口和计量流程；分期和待拍板的事项。

## 一、现状

| 方面     | 现在                                                                                 | 商业化前要解决的问题                                                                                                  |
| -------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| 账号     | 手机号加验证码或密码；`users` 表只有手机号和密码                                     | 没有停用、昵称、管理员；客服只能登服务器查库                                                                          |
| 官方模型 | 环境变量配置一个上游地址、一个密钥和模型列表（`OFFICIAL_MODELS_JSON`）；登录后就能用 | **不计量、不限量、不留记录**。上游密钥一旦配上，任何账号的一个 Agent 循环都可能把账单跑满，也算不出每个用户花了多少钱 |
| 模型密钥 | 客户端把 15 分钟有效的登录令牌当作官方模型的密钥                                     | 长时间的 Agent 对话可能中途失效；也没法单独吊销某台设备的模型调用                                                     |
| 同步空间 | 文件存在阿里云 OSS，同一项目内按内容去重；单个文件不超过 200 MB                      | 没有总量统计和上限，存储和下载流量的成本没有上限；也没清理没人引用的文件                                              |
| 团队     | 没有“团队”这个对象：有其他成员的项目就是团队项目，成员按手机号邀请                   | 课题组没法统一付费、统一管理；后台也看不到谁和谁在协作                                                                |
| 运营     | 没有后台                                                                             | 开通、补偿、封禁、对账都没有入口                                                                                      |

结论：**在官方模型对外开放之前，必须先有计量、额度和后台**。这是第一期的全部内容。

## 二、原则

- **本机功能永远免费**：阅读、编辑、实验、写作、导出和数据迁出不设付费墙（见[产品定位](../01-产品定位与功能模块.md)第八节）。用户填自己的模型密钥，用多少都不经过我们，也不扣额度。
- **只对要花钱的服务收费**：官方模型、云同步空间、课题组的统一管理和发票、院校私有化部署。
- **额度看得见**：用户随时能看到剩多少、每一轮用了多少、什么时候重置。额度用完时明确告诉用户，不偷偷换成更便宜的模型。
- **不删用户的数据**：套餐到期或空间超出时，只暂停上传，不删云端文件，不锁本机文件，下载照常。
- **后台看不到研究内容**：后台只看账号、计量和元数据（项目名、文件数、大小）。论文、文档、代码和 AI 对话的内容，后台既不存也不显示。
- **先手动开通，再在线支付**：第一期用兑换码和管理员开通验证付费意愿，第二期再接微信支付和支付宝。

**为什么是这几个数**：

- **个人专业版**：3,000 点按售价约等于 ¥30。按经济模型算，一轮带论文的 Agent 对话约 15 点，一个月约 200 轮；按标准模型约 50 轮。模型的售价约为成本的 2 倍，所以就算用户用满，模型成本也只有约 ¥15。
- **免费版**：300 点约 20 轮，够体验，不够当主力。
- **价格锚点**：同类产品里，Papers AI Plus 是 £10/月，国内研究生对 ¥20–40/月更容易接受。年付打约 8 折。

## 四、额度

### 1. 计量单位：点

- **用户看到的是“点”**：1 点按售价算等于 ¥0.01，1,000 点就是 ¥10。
- **不用 token**：研究者不懂 token，而且不同模型的单价差几十倍，同样的 token 数没有可比性。
- **不按次数计**：一轮 Agent 对话可能只读几百字，也可能读完一篇 30 页的论文，按次收费对两边都不公平。

### 2. 模型价格

每个模型在后台配置下面这些价格，单位都是“每百万 token”：

| 价格   | 怎么算                                                 | 例子（DeepSeek V3.2，虚构价格） |
| ------ | ------------------------------------------------------ | ------------------------------- |
| 成本价 | 上游的价格，分输入、缓存命中的输入、输出三项，单位是元 | ¥2 / ¥0.2 / ¥3                  |
| 售价   | 用户被扣的点数，同样分三项；思考过程的 token 按输出算  | 400 / 40 / 600 点               |
| 毛利率 | 后台按两者自动算出，低于设定值（例如 30%）时标红       | 50%                             |

在模型菜单里，用户看到的是**相对默认模型的倍率**，例如“1×”“3×”，比每百万 token 多少点好懂。

### 3. 额度从哪来

| 来源         | 什么时候发                   | 有效期                 |
| ------------ | ---------------------------- | ---------------------- |
| 套餐月度额度 | 每个计费周期开始时           | 到本周期结束，不累积   |
| 加油包       | 购买后                       | 12 个月                |
| 赠送         | 注册、兑换码、活动、客服补偿 | 发放时设定，默认 90 天 |
| 人工调整     | 管理员加减，必须写原因       | 发放时设定             |

每一笔都单独记账（“额度包”），各自记着剩余和到期时间。

### 4. 扣费规则

- **先扣最早到期的**：这样用户最划算，也不用额外解释。
- **按实际用量扣**：一次请求结束后按上游报告的 token 数扣。用户中途停止的，按已经生成的部分扣；上游报错、没有生成内容的，不扣。
- **余额不足时**：余额小于等于 0 时，不再接受新请求；正在进行的请求让它做完，允许出现小额欠额，下次有额度时先抵扣。不在一轮 Agent 对话中间突然掐断，否则文件可能只改了一半。
- **周期滚动**：月度额度在周期结束时作废，作废也记一笔流水，用户能查到。

### 5. 防失控

下面这些是**保护措施，不是收费点**。默认值按套餐设，后台可以给单个用户单独调。

| 限制           | 免费      | 专业版    | 为什么                                                                   |
| -------------- | --------- | --------- | ------------------------------------------------------------------------ |
| 每分钟请求数   | 30        | 60        | 防止 Agent 死循环；一轮 Agent 对话会连续发很多次请求                     |
| 同时进行的请求 | 2         | 4         | 多个对话可以并行，但不能无限并行                                         |
| 单日上限       | 400 点    | 1,000 点  | 一个失控的晚上不会把整月额度用光；免费版放宽到能一天用完注册赠送的一部分 |
| 单次最大输出   | 32k token | 32k token | 只压低超过它的请求，不替没要求的请求加上限，避免上游拒绝                 |

## 六、管理后台

### 1. 访问方式

- **地址**：由协作服务直接提供，地址是 `https://124.221.115.83:8443/admin`。域名备案后改用独立域名。页面是静态文件，和接口同源，不需要跨域。

### 4. 团队的可视化

现在没有“团队”对象，所以团队从协作关系里推出来：

- **协作关系图**：每个用户一个点，两个人共同在某个项目里就连一条线，共同的项目越多线越粗。点的大小表示本月 AI 用量。连在一起的一群人就是一个团队，用其中拥有团队项目最多的人命名，例如“张老师的团队”。只有自己的个人项目的用户不出现在图里。
- **团队列表**：和图一一对应。列出名称、所有者、成员数（按角色分）、团队项目数、空间、本月用量、最近活跃、所有者的套餐。图和表都可以点进同一个详情页。
- **团队详情**：
  - **成员 × 项目矩阵**：每格是这个人在这个项目里的角色，空格表示不在这个项目里；
  - **活动热力图**：成员 × 最近 30 天，颜色越深表示当天同步推送的次数越多；
  - **成员用量**：本月每个人用了多少点；
  - **空间构成**：按文献、代码、文档、笔记和其他分开显示。

第三期有了“课题组”对象以后，课题组直接按组织显示，推断出来的团队仍然保留，用来发现可能会购买课题组版的团队。

## 七、计量流程

官方模型的每次请求都经过协作服务：

1. **鉴权**：用专用的模型令牌（见下文）找到用户，检查账号是否停用。
2. **找模型**：把对外的模型名换成渠道和上游模型；检查用户的套餐是否包含这个模型。
3. **检查额度和限制**：所有未过期额度包的剩余加起来必须大于 0；单日上限、每分钟请求数和同时进行的请求数都没超。不通过时返回带 `code` 的错误，客户端按 `code` 显示对应的卡片：

| 情况             | 状态码 | `code`              |
| ---------------- | ------ | ------------------- |
| 额度用完         | 402    | `quota_exhausted`   |
| 套餐不含这个模型 | 403    | `model_not_in_plan` |
| 请求太频繁       | 429    | `rate_limited`      |
| 到了单日上限     | 429    | `daily_limit`       |
| 账号已停用       | 403    | `account_disabled`  |

4. **转发并计数**：边转发边读事件流。Responses 接口取 `response.completed` 里的用量（输入、缓存命中、输出、思考）；Chat Completions 接口在请求里加上 `stream_options.include_usage`，取最后一个事件里的用量。上游没报告用量时（例如用户中途停止），按字数估算，并标记为“估算”。
5. **记账**：在一个事务里写入这次请求的用量记录，按到期顺序扣额度包（锁住该用户的额度包，避免并发请求重复扣），写入流水，更新按天汇总的用量表。
6. **按项目统计**：客户端通过请求头带上项目 ID（Codex 的模型服务配置支持固定的请求头），用量就能按项目汇总。

**模型令牌**：客户端申请一个只能调用模型和读额度的长期令牌，每台设备一个，可以在“账号与订阅”和后台里吊销。这样长对话不会因为 15 分钟的登录令牌过期而中断。令牌只放在内存里，每次启动应用重新申请一个，服务器同时作废这台设备的旧令牌；退出登录时吊销。

**定时任务**（在服务进程里运行，只有一个实例）：

- **每小时**：作废过期的额度包，并记流水；
- **每个计费周期开始**：发放月度额度。如果定时任务漏跑了，用户的第一次请求也会补发；
- **每天**：汇总用量；清理没有任何同步记录引用的 OSS 文件；生成对账数据，用于和上游账单比对。

## 八、同步空间

- **怎么算**：一个项目占用的空间是它在 OSS 上所有未删除文件的大小之和，同一项目里内容相同的文件只算一次，历史版本引用的文件也算在内。一个人占用的空间是他拥有的所有项目之和。上传完成和删除时更新项目的占用量，不必每次都重算。
- **怎么限**：申请上传地址时，如果所有者的占用量加上这个文件超过上限，就返回 `storage_full`；不影响下载和记录同步。
- **降级以后**：超出的部分不删，只是不能再上传新文件，直到所有者升级或清理。
- **历史版本保留期**：按套餐清理超过保留期的旧版本（只清服务端的历史，不动当前文件）。

## 十一、代码结构

- **服务端拆文件**：现在的 `server/src/server.mjs` 一个文件有 735 行，按功能拆成 `routes/`（账号、项目、同步、模型）、`billing/`（价格、计量、额度、限制）、`admin/`（会话、接口、审计）和 `jobs.mjs`。继续用 Node 自带的 `http`，只加一个很小的路由函数，不引入框架。
- **后台页面**：放在 `server/admin/`，用浏览器原生的 JavaScript 模块写，不需要构建，和桌面应用使用同一套颜色。由服务端在 `/admin` 下提供，部署脚本把它和 `src/` 一起上传，服务器上不需要前端工具链。仓库是公开的，后台代码里不放任何密钥。
- **客户端**：`src/features/account/` 加“账号与订阅”页；`features/assistant/` 处理带 `code` 的错误卡片、模型倍率和本轮用量；`platform/collaboration.ts` 加计费接口和模型令牌。
- **测试**：服务端用临时 PostgreSQL 测试并发扣费（同一用户 20 个请求同时结束，余额正确且不重复扣）、到期顺序、欠额、估算、周期滚动、兑换码只能用一次、各角色的权限、审计记录；客户端测试各种错误卡片。

后台的做法参考了 easyNote 已经上线的管理后台（静态页面由服务端提供、按用户按天按模型计量、单独设置用户上限），但 Scientify 多了额度包、套餐和团队，不直接复用代码。

## 十四、风险

- **上游涨价或降价**：在后台改成本价和售价即可，已经发出去的额度不变。毛利率低于设定值时，概览页会提醒。
- **估算不准**：只有上游不报告用量时才估算，估算的请求都有标记，对账时单独统计。如果估算的比例超过 5%，就要查是哪个渠道的问题。
- **并发扣费**：扣费时锁住该用户的额度包，测试里覆盖同时结束的多个请求。
- **旧版本客户端**：旧版本还在用 15 分钟的登录令牌调用官方模型。第一期服务端仍然接受这种令牌，同样计量和限额；第二期再停止接受。
